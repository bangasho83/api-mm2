STU-Storage

Architectural uncertainty in designing a storage layer for retroactively-mutating multi-source data serving heterogeneous consumer classes under multi-tenant SaaS economics.

Ingestion Storage Orchestration Generation

Scientific and Technological Uncertainty (STU)

It was not known whether a single storage architecture could simultaneously satisfy three constraints that are in structural tension: absorbing retroactive metric mutations from external APIs, serving heterogeneous consumer classes (operational vs. analytical) with different latency and consistency requirements, and remaining economically viable under multi-tenant SaaS load.

H1 — NoSQL Document Store (Firestore as Sole Layer)

Firestore used as the primary and only storage layer for all data classes: metrics, brand profiles, org configs, backlinks. Retroactive metric mutation (Meta spend revision, GA4 session reattribution) required full document rewrites. Composite query requirements surfaced as runtime index errors not detectable at write time.

// services/firebase-service.js : 19
// H1: Firestore as sole storage layer

// ALL data classes stored as Firestore documents:
//   metrics, brands, orgs, pages, backlinks
// FAILURE 1: retroactive mutations require full doc rewrites —
//   no diff/patch primitive in Firestore.
// FAILURE 2: composite index requirement surfaces at query time,
//   not at write time — runtime failure for multi-field range queries.
// services/firebase-service.js : 316–350
// PSEUDOCODE: H1 — composite index failure at runtime
try {
  let query = backlinksRef.where('brandId', '==', brandId);
  if (fromDate) query = query.where('createdAt', '>=', fromTimestamp);
  if (toDate)   query = query.where('createdAt', '<=', toTimestamp);
  querySnapshot = await query.get();   // FAILS if composite index not pre-built
} catch (indexError) {

H2 — Relational Database with Partitioning and Materialised Aggregates

Postgres evaluated with tenant-partitioned tables and materialised views for aggregate queries. Partitioning addressed query performance for analytical consumers, but retroactive metric mutation invalidates materialised views — UPDATE on historical partitioned rows triggers partition rebuild, which defeats the materialisation.

-- PSEUDOCODE: H2 — Postgres design-phase evaluation
-- Partition by (tenant_id, date_month) for query locality
CREATE TABLE ad_metrics (
  tenant_id    UUID        NOT NULL,
  date         DATE        NOT NULL,
  spend        NUMERIC,
  impressions  BIGINT,
  conversions  BIGINT
) PARTITION BY RANGE (date_month);

-- Materialised view for analytical consumers
CREATE MATERIALIZED VIEW monthly_spend AS
  SELECT tenant_id, date_trunc('month', date) AS month, SUM(spend) AS total_spend
  FROM ad_metrics GROUP BY 1, 2;

-- NEGATIVE RESULT:
-- Meta retroactively revises spend figures after attribution window.
-- UPDATE on historical rows triggers partition rebuild → REFRESH MATERIALIZED VIEW
-- required on every retroactive mutation. Materialisation overhead exceeds benefit.

H3 — Warehouse-Class Storage (Snowflake, BigQuery, Redshift)

Snowflake, BigQuery, and Redshift evaluated for the analytical consumer class. All three share the same structural negative result: MERGE/UPSERT primitives exist but require the ingestion layer to supply the delta record. The warehouse cannot detect or absorb retroactive mutation independently.

-- PSEUDOCODE: H3 — Warehouse MERGE evaluation (BigQuery / Snowflake)
MERGE INTO ad_metrics AS target
USING (SELECT * FROM incoming_delta) AS source
ON target.tenant_id = source.tenant_id
  AND target.date = source.date
WHEN MATCHED THEN
  UPDATE SET spend = source.spend, conversions = source.conversions
WHEN NOT MATCHED THEN
  INSERT (tenant_id, date, spend, conversions)
  VALUES (source.tenant_id, source.date, source.spend, source.conversions);

-- NEGATIVE RESULT (corollary, applies to all three warehouses):
-- MERGE/UPSERT exists but requires ingestion layer to produce a delta record.
-- If Meta silently revises a historical figure, the warehouse has no mechanism
-- to detect the change — it only absorbs what the ingestion layer delivers.
-- The retroactive mutation problem is not a storage problem; it is an ingestion
-- detection problem. No warehouse-class primitive solves it natively.

STA ACHIEVED

H4 — Tiered Architecture with Mutation Absorbed at the Projection Layer

Retroactive mutation absorbed at the projection (read) layer via client-side filtering — storage documents are not rewritten on mutation. Consumer-class TTL stratification (operational vs. analytical) implemented via two separate cache tiers with different invalidation intervals.

// services/firebase-service.js : 353–374
// PSEUDOCODE: H4 — mutation absorbed at projection layer, not at storage
backlinks.forEach(doc => {
  const data = doc.data();
  if (fromDate || toDate) {
    const createdAt = data.createdAt.toDate
      ? data.createdAt.toDate()
      : new Date(data.createdAt);
    // Projection layer applies date filter — storage doc is NOT rewritten.
    // Retroactive mutation is a read-time recalculation, not a write-time update.
    if (fromDate && createdAt < new Date(fromDate + 'T00:00:00.000Z')) return;
    if (toDate   && createdAt > new Date(toDate   + 'T23:59:59.999Z')) return;
  }
  backlinks.push({ id: doc.id, ...data });
});
// services/firebase-service.js : 595–609
// PSEUDOCODE: H4 — workload-classification model, two cache tiers
const BRAND_CACHE = { data: {}, timestamps: {}, TTL: 1  * 60 * 1000 };
//   ↑ operational consumer class: brand resolution on every API call
//     requires fresh data — 1-minute TTL

const ORG_CACHE   = { data: {}, timestamps: {}, TTL: 15 * 60 * 1000 };
//   ↑ analytical consumer class: org-level billing aggregates tolerate
//     15-minute staleness — longer TTL reduces Firestore read load

// Workload classification determines TTL; TTL is not shared across consumer classes.

✓ STA: Retroactive mutation absorbed at the projection layer, not at storage. Consumer-class stratification implemented as a workload classification model. Corollary negative result documented: no warehouse-class storage primitive absorbs retroactive metric mutation natively.

Scientific and Technological Advancement (STA)

Workload-classification model for tiered storage architecture. Retroactive mutation absorbed at the projection layer rather than at storage, decoupling storage write semantics from consumer read semantics. Consumer classes stratified by workload type (operational vs. analytical), each assigned an independent TTL policy derived from classification. Corollary negative result: no warehouse-class storage primitive (Postgres, Snowflake, BigQuery, Redshift) natively absorbs retroactive metric mutation — MERGE/UPSERT requires the ingestion layer to supply the delta. This finding is transferable: any SaaS data platform ingesting retroactively-mutating external metrics must absorb mutation at the projection layer, not at storage.
